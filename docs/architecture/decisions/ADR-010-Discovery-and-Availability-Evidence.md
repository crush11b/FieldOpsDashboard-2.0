# ADR-010: Discovery and Availability Evidence

- Status: Accepted for V2.9-03
- Date: 2026-09-11
- Scope: server-side application discovery and runtime availability evidence

## Decision

V2.9-03 replaces the dishonest `/api/apps/detect` behavior with `POST /api/apps/discover`, a typed, local-only route that returns bounded, truthful discovery evidence for a set of catalog application IDs. The previous implementation invented OS-specific installation paths, reported `installed: true` by fallback for any unrecognized app, and returned hard-coded version strings that were never observed. None of that behavior is preserved.

Discovery is performed entirely server-side against trusted, server-owned records. The browser may only supply a bounded array of catalog IDs (`ids`); the request body must be a plain object containing exactly that one field. Each ID must also satisfy the existing App Catalog stable-ID grammar from `isStableApplicationId` (lowercase ASCII letters, digits, and hyphens only, beginning with a letter or digit). Values such as `__proto__`, path-like IDs, whitespace-containing IDs, and uppercase IDs are rejected. Any other field &mdash; an application object, an executable path, arguments, a working directory, or an operating-system claim &mdash; is rejected with an explicit `invalid_request` result rather than being silently ignored. The route derives each application's `AppCatalogTarget` from the existing trusted `AppLauncherItem` configuration using the pure `toCatalogRecord` conversion already defined by ADR-008, so discovery reuses the same native/web/unsupported target vocabulary and never accepts a browser-constructed target.

## Evidence model

Discovery produces one `AppDiscoveryObservation` per requested ID in `src/appCatalog/discovery.ts`, reusing the existing `CatalogTruth` and `LaunchOutcome` types from the App Catalog domain contract (ADR-008) rather than inventing a parallel vocabulary. Each observation carries `configured`, `enabled`, `detected`, `installed`, and `available` (each independently `yes` / `no` / `unknown` / `unsupported`), a `launch` field that is always `unknown`, an `evidenceSource` (`configured_path`, `candidate_path`, `configured_web_target`, `unsupported_target`, `disabled_record`, `unknown_id`, or `probe_error`), a bounded human-readable `reason`, and an `observedAtUtc` timestamp. Evidence is never persisted; it is computed fresh on every request and is not written into `DashboardConfig` or any durable catalog record.

State semantics are explicit and independently representable:

- **configured** is a durable property of the target: `yes` for a native record with a non-empty `executablePath`, or a web record with a structurally valid HTTP/HTTPS URL; `no` for an unconfigured, invalid, or unsupported target. It is unrelated to whether discovery ever probed anything.
- **enabled** reflects the record's durable enablement, independent of its target: `yes` for an enabled record, `no` for a disabled record, and `unknown` when the ID does not resolve to any record at all.
- **detected** means a bounded, explicit probe found genuine evidence (a real file, for native targets). It does not mean the software is fully installed or licensed.
- **installed** is never inferred from the file probe. A discovered executable file may still produce `installed: unknown`; a file probe alone can prove `detected`/`available`, but never `installed`. Production has no independent installation-evidence source wired up yet, so `installed` is always reported as `unknown` for native targets unless a caller injects an `InstallationEvidenceProvider` (a separate, explicitly independent evidence source, e.g. a package registry). An absence at the bounded candidate paths is evidence only about those specific paths and must never be read as proof that the application is not installed anywhere else on the system.
- **disabled records** are never probed. `enabled` is `no`, `detected`/`installed` are `unknown`, and `available` is `no`, with `evidenceSource: disabled_record`.
- **available** additionally accounts for enablement and whether the current launcher can use the detected target. A configured executable path that is found produces `detected: yes`, `available: yes`. A configured path that is missing while a server-owned candidate path is found produces `detected: yes`, `available: no`: the candidate proves detection only, and the current launcher cannot use it until a later slice updates the configured path. It never implies a successful launch.
- **launch outcome** is never synthesized from discovery. Discovery always reports `launch: unknown`; only a real launch attempt through `server/launcher.ts` (ADR-009) can report `Launched`, `LaunchFailed`, `Busy`, etc. The two evidence families are computed independently and neither overwrites the other.
- **web targets are not locally installed.** `detected` and `installed` are always `unsupported` for web targets. A structurally valid HTTP/HTTPS URL is `configured: yes`, but `available` remains `unknown` because no network reachability check is ever performed. An invalid or malformed web target is `configured: no` and `available: no`.
- **unsupported targets** (legacy or unconfigured) remain explicit (`unsupported`) rather than being coerced into a native or web state, and are always `configured: no`.
- **unknown IDs** (no matching record) report `configured: no`, `enabled: unknown`, and `detected`/`installed`/`available: unknown`, with `evidenceSource: unknown_id`.

## Bounded probe strategy

Native discovery probes, in order: the record's configured `executablePath` (if any), then up to `APP_DISCOVERY_MAX_CANDIDATE_PATHS` (8) server-owned candidate paths from a small curated, Windows-only table (`WINDOWS_CANDIDATE_PATHS` in `server/appDiscovery.ts`) keyed by stable catalog ID. A configured executable file proves both detection and availability to the current launcher. A candidate-only file proves detection but not availability, because the current launcher still resolves the configured path and cannot use the candidate until a later slice updates configuration. Candidate paths are only ever used as probe input; a match is evidence, never an installation action, and the matched path is never written back into `DashboardConfig` or applied to any application's configured `executablePath`. A miss across every bounded candidate path proves absence only at those specific locations, never installation status elsewhere, which is why `installed` is not derived from this probe at all. `statAppFileProbe` uses `fs.statSync` to verify an actual file (not a directory or merely a constructed string) exists at each candidate, distinguishing `file`, `directory`, `missing`, and `error` (e.g., permission denied) outcomes. Probe errors are reported as `unknown` evidence rather than being interpreted as either present or missing. No directory is recursively scanned, no package manager or installer is invoked, and no shell command is executed.

Requests are bounded: at most 50 requested IDs, each at most 128 characters, deduplicated before evidence is computed; unknown IDs and malformed request bodies return an explicit `invalid_request` result. The discovery route is loopback-only, matching the existing `/api/config` and `/api/apps/launch` trust boundary (ADR-006, ADR-009).

## Runtime-only lifecycle and relationship to launcher outcomes

Discovery evidence lives entirely in the HTTP response for the request that produced it. It is not cached, persisted, or merged into `DashboardConfig`, and it never sets `AppLauncherItem.installed` or mutates `executablePath`. This preserves the existing durable configuration schema unchanged. Launch outcomes (ADR-009) remain a completely separate evidence family produced only by an actual launch attempt through the Tray named-pipe protocol; discovery never claims a launch occurred, and a successful discovery observation is never substituted for a launch result.

## Legacy UI

`src/components/AutoAppInstallerModal.tsx` is prototype/legacy UI that is not imported or rendered anywhere in `App.tsx`; it is unreachable in the running application. Its detection call previously targeted the retired `/api/apps/detect` route and applied fabricated paths directly into dashboard configuration (`installed: true`, `executablePath` overwrite) &mdash; the exact unsafe legacy mutation this slice prohibits. Because the component is unreachable, no runtime behavior changes for any operator, and no adapter was required to satisfy V2.9-03. Reclassifying or rewriting this legacy surface remains the disposition of the V2.9-08 punch-list item ("Legacy Auto App Installer presentation") and is out of scope here.

## Consequences

`POST /api/apps/discover` supplies truthful, bounded evidence to any future catalog-management UI (V2.9-04) without pre-committing to a UI contract. `AppCatalogRuntimeState`/`AppCatalogRuntimeStates` (ADR-008) remain the durable-adjacent runtime-state shape for the eventual catalog cutover; `AppDiscoveryObservation` is the richer, evidenced shape this slice actually returns and MAY be projected into `AppCatalogRuntimeState` by a later slice. This ADR does not authorize catalog persistence, catalog management UI, curated catalog migration, application installation, generated installation scripts, package-manager execution, recursive drive scanning, automatic radio-hardware detection, or any change to the Tray launcher protocol.
